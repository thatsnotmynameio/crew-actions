## Planning Contract

### Key Technical Decisions

- KTD3. **The file is parsed by walking a `yaml.Node`, with `go.yaml.in/yaml/v3`.** v3 is the maintained continuation of `gopkg.in/yaml.v3`, the one crew uses. The only YAML module already in `go.mod` is v4, an indirect release candidate. Decoding into a node and checking each mapping's keys against the keys allowed at that level (workflow: `steps`; step: `name`, `commands`) gives an error type that carries the key, its path (`steps[1].comands`) and its line. Part 4 then sorts a refused key into "not supported yet" or "unknown" (R8), and part 5 adds `retry` (R7), without parsing an error string. Rejected: a strict struct decode (`KnownFields`), whose error is a string naming a Go type.
- KTD4. **`spec` takes bytes and a name, never a path it opens.** `spec.Parse(name, content)` builds the workflow, and a pure `spec.NameFromPath(path)` derives the name (R6) by removing a final `.yaml` or `.yml`. The engine receives the file's content from `run` (part 4), and #19 denies `os` to `spec`. Names are taken from the path's base: `ci/test.yaml` gives `test`, `a.b.yml` gives `a.b`. Any other extension, no extension, or an empty stem is an error, since slice 2 will read only `.yaml` and `.yml` files from `.crew/workflows/`.
- KTD5. **The format refuses what it cannot run as written.** The file is one YAML document whose root is a mapping. It has at least one step. Each step name is non-empty, unique in the workflow, and free of newlines and control characters, because part 4 prefixes output lines with it (R3). Each step has at least one command. A command is a non-blank scalar with no NUL byte, kept as the text written, so `- 123` runs `123`. A command that YAML reads as a mapping, the usual result of an unquoted `: `, is refused with its line and a hint to quote it. Every error names its path and line.
- KTD6. **A step is one POSIX shell, `/bin/sh -c`, with an exit-status check after each command.** The backend builds the script: each command, a blank line, then a line that exits with the command's status when it is not zero. `cd` and `export` carry across a step's commands, as authors of multi-command steps expect, but not into the next step. Every step starts at the workspace's root. The blank line ends a command that finishes with a `\` line continuation before the check. Each command must be a complete shell command on its own: a heredoc ends inside its command, and no command ends with `|`, `&&` or `||`. Otherwise the commands and checks after it become part of it, and the step can exit 0 without running them. A step's exit status is that of its failing command (R6). A command that runs `exit 0` ends its step with success and skips the step's remaining commands. Rejected: one shell per command, which loses `cd` and `export` between commands. Rejected: a `set -e` script, which does not stop on a failure inside an `&&` list, contrary to R6. Rejected: an `eval` loop over positional arguments, which shows the other commands in `$@`, lets `break` end the step with success, and turns off a user's `set -e`.
- KTD12. **Errors are wrapped where they cross a package.** `wrapcheck` runs, and its ignore list names crew's module, not this one. Wrapping costs nothing, and changing the lint config is #19's.

### High-Level Technical Design

The file format, as a reader writes it, in `test.yaml`, so the workflow is named `test`:

```yaml
steps:
  - name: build
    commands:
      - cd src
      - make
  - name: check
    commands:
      - ./scripts/check.sh
```

### Assumptions

These are inferred, unconfirmed bets.

- Until part 4 adds the "not supported yet" class (R8), every key outside this format is refused as unknown. Accepting extra keys for now would run a file with an effect silently dropped, which the parent's Key Decisions forbid.
- `/bin/sh` is the only shell, and the format has no `shell` key. Bash-only syntax (`[[`, `pipefail`) works on macOS, where `/bin/sh` is bash, and fails on Linux, where it is dash. The package documentation says steps run under POSIX sh.
- Step names must be unique. Loosening that later is compatible, and tightening it later is not.

## Implementation Units

### U2. The workflow file format in internal/spec

**Goal:** a workflow file's content becomes a validated workflow with its steps, or an error naming the path and line at fault.

**Requirements:** R6; KTD3, KTD4, KTD5, KTD12.

**Dependencies:** none.

**Files:**
- Modify `go.mod` and `go.sum` (add `go.yaml.in/yaml/v3` as a direct dependency).
- Create `internal/spec/spec.go` and `internal/spec/spec_test.go`.

**Approach:**
- The package documentation states the format, that a step's commands run in one POSIX shell from the workspace's root, and that each command must be a complete shell command on its own (KTD6), so authors find the rules next to the code.
- The workflow and step types are plain values: the workflow's name and its steps, each step's name and commands in order.
- The refused-key error is an exported type that carries the key, its path and its line, so part 4 can classify it (KTD3).
- The package imports nothing that does I/O.

**Patterns to follow:** crew's `internal/config/decode.go` for walking `yaml.Node` and reporting paths and lines.

**Test scenarios:**
- A file with two steps of two commands each parses into a workflow named by `NameFromPath`, with the steps and commands in file order.
- `NameFromPath` gives `test` for `test.yaml`, `test.yml` and `./ci/test.yaml`, and `a.b` for `a.b.yaml`.
- `NameFromPath` refuses `test`, `test.json`, `test.YAML` and `.yaml`.
- A step key `comands` is refused with the refused-key error, whose key is `comands`, path `steps[0].comands`, and line the line of that key.
- A top-level key `depends_on` is refused with the same error type, path `depends_on`.
- An empty file, a file holding only comments, and a `null` document are refused.
- A top-level list and a top-level scalar are refused as not a mapping.
- Two YAML documents in one file are refused.
- A missing `steps`, `steps: null` and `steps: []` are refused.
- A null step entry is refused with its index in the path.
- A missing, empty or whitespace-only step name, and one containing a newline, are refused.
- Two steps with the same name are refused, naming the second one's path.
- Missing `commands`, `commands: []` and `commands: "echo hi"` (a scalar, not a list) are refused.
- A null, empty or whitespace-only command is refused.
- `- 123` and `- true` are kept as the commands `123` and `true`.
- `- echo key: value` is refused with its line and a hint to quote the command.
- A command holding a NUL byte (`"a\0b"`) is refused.
- A duplicate key in one mapping is refused.

**Verification:** every scenario passes, and the package imports neither `os` nor any `crew-actions` package that does I/O.
