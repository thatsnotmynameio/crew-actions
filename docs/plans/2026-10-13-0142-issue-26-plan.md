## Planning Contract

### Key Technical Decisions

- KTD1. **One `depguard` rule per import rule, deny lists only.** Each of the eight import rules becomes one named rule with a `deny` list, except the OpenTelemetry rule, which KTD5 splits in two, for nine rules in all. No rule uses `allow` or `list-mode: strict`. An allow list would have to name every standard and third-party package a pure package may use, including the YAML library `spec` has not picked yet. Rules are independent: depguard reports an import when any rule whose files match denies it.
- KTD2. **No entry in a deny list is a prefix of another entry in the same list, unless it ends in `$`.** depguard v2.2.1 sorts each list and compares an import against only the nearest entry before it (`strInPrefixList` in `settings.go`). So `os` next to `os/exec` would let `os/signal` through. One prefix per subtree (`os`, `log`) covers the whole subtree. `$` marks an exact match where a subtree must stay open, as with `net$`, which leaves `net/url` and `net/netip` allowed.
- KTD3. **A path whose name is the start of another package's name is written as two entries, `<path>$` and `<path>/`.** Matching is a plain string prefix. So crew is denied as `github.com/thatsnotmynameio/crew$` plus `github.com/thatsnotmynameio/crew/`, because a bare `github.com/thatsnotmynameio/crew` would flag every import of `github.com/thatsnotmynameio/crew-actions/...`. In the same way, `internal/proc` is written as `internal/proc$` plus `internal/proc/`, because a bare `internal/proc` would also deny `internal/protocol`, which already exists.
- KTD4. **"Nothing that does I/O" is a deny list of the standard library's I/O packages plus the internal packages that do I/O.** The standard library list is `os`, `net$`, `net/http`, `net/rpc`, `net/smtp`, `syscall`, `database/sql`, `io/ioutil` and `log`. The internal list is `engine`, `store`, `transport`, `api`, `source`, `runner`, `telemetry` and `proc` (written per KTD3), under `github.com/thatsnotmynameio/crew-actions/internal/`. `telemetry` is included because section 8 says pure packages open no span. Third-party I/O libraries (pgx, goose, connect-go, OpenTelemetry) are already denied to these packages by their own "only X imports Y" rules, so this list does not repeat them. The rule excludes `$test`, so tests in `spec` can read fixtures from `testdata`.
- KTD5. **OpenTelemetry is two rules.** The first denies `go.opentelemetry.io` everywhere except `internal/telemetry` and `cmd/crew-actions` (D13). The second denies the exporters (`go.opentelemetry.io/otel/exporters` and `go.opentelemetry.io/contrib/exporters`, which holds autoexport) everywhere except `cmd/crew-actions` (D14). The SDK packages themselves stay open to `internal/telemetry`, so it can offer an in-memory span recorder that other packages' tests use without importing OpenTelemetry. A provider with no exporter exports nothing, so D14 still holds.
- KTD7. **Rules other than the I/O rule also apply to test files.** The architecture states the rules for packages, not for production code alone. A test that needs the engine and a runner together lives where both may be imported, such as `cmd/crew-actions`.

Directional. The implementer picks the YAML shape. Every `desc` ends with the decision it cites. Paths are under `github.com/thatsnotmynameio/crew-actions/internal/` unless they are third-party.

### Assumptions

- R24's "crew's rules and comments" covers the `depguard` block and the header comment at lines 3–4, as the issue's Sources name. Other crew-specific text in `.golangci.yml` stays: the comments under `linters.disable` (`ireturn`, `tagliatelle`, `testpackage`, `err113`, `gosmopolitan`, `paralleltest`) and `wrapcheck.ignore-package-globs`, which still names `github.com/thatsnotmynameio/crew/*`.
- "The import rules of section 4" means the eight bullets under "Import rules, checked by `depguard` (D7)". Constraints stated only in the package descriptions get no rule here: `scheduler` takes no `context.Context`, and `proc` is the one way to start a child process.
- sqlc's generated code lives under `internal/store/postgres/`. If the store part puts it elsewhere, that part adds its path to the postgres rule.
- `docs/architecture.md` needs no change. This part enforces section 4 as written and settles no question from "Open, and who decides it". KTD5's reading of "sets up its SDK" as "imports an exporter" is the one interpretation, and part 7 can write it down when it rewrites the document.

### Risks

- **Generated connect-go stubs.** `protoc-gen-connect-go` output imports connect-go, and the protocol part may generate it under `internal/protocol/`. golangci-lint v2.14.0 excludes issues in generated files by default: `linters.exclusions.generated` defaults to `strict`, which matches the `// Code generated ... DO NOT EDIT.` header that protoc-gen-connect-go writes. This config does not override that, so the stubs should not trip the connect rule. If they do, the protocol part moves the stubs or adds an exclusion with its reason.
- **Rules for third-party packages cannot be shown to fire in this repository.** pgx, goose, connect-go and OpenTelemetry are not in `go.mod`, and a probe that imports them fails to type-check before depguard runs. U1's verification covers this with a scratch copy of the repository. Go itself forbids importing crew's `internal/` packages, so the crew rule can only be checked for false positives: every probe import of `crew-actions` must pass it.
