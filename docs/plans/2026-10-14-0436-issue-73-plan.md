## Planning Contract

### Key Technical Decisions

- KTD2. **The protocol has five calls in this part: `next`, `accept`, `update`, `log` and `done`.**
  - `next` returns a workflow's id, the version `AssignWorkflow` returned, its name and its resolved steps (names and commands), or nothing.
  - `accept` takes the workflow id and that version and returns the attempt id.
  - `update` takes the attempt id, a 1-based step position, the state (`running`, `finished` or `skipped`), the outcome, and an exit status or none.
  - `log` takes the attempt id, the position, a byte offset and at most 64 KiB of data, and returns the size the engine now holds (KTD7).
  - `done` takes the attempt id and the outcome.

  The runner maps the executor's 0-based index to the 1-based position, and its exit status -1 to none, in one adapter. The engine refuses a position outside the attempt's steps.
- KTD3. **The stored definition is the compiled workflow, encoded as the protocol's `Workflow` message.** The engine runs `spec.Parse` once, at submit, which is where R8's refusal happens. It stores the name and resolved steps that `next` hands out and `accept` takes the step names from, as `model.Workflow.Definition`'s comment and the first migration already describe. Rejected: storing the file and parsing it again at hand-out, where a file a newer parser refuses would roll back the hand-out and stall the queue behind the oldest pending workflow.
- KTD4. **Errors cross HTTP as a small vocabulary of `internal/model` sentinels.** The engine returns `ErrConflict`, `ErrNotFound`, a new `ErrInvalid`, which wraps a message that is safe to show, or a new `ErrUnavailable` when it is stopping. `transport/connect` maps them to `Aborted`, `NotFound`, `InvalidArgument` and `Unavailable`, and back. A request over the size limit (`ResourceExhausted`) comes back as `ErrInvalid`. A non-remote error, such as a refused connection or a stream cut by a dying server, also comes back as `ErrUnavailable`. Any other error reaches the client as `Unknown` with no message, so internal detail never leaks. When the caller's own context is done, the client returns the context's error, never `ErrUnavailable`, so a Ctrl-C is never retried. The runner and `run` branch on these sentinels with `errors.Is` and never see a connect code.
- KTD5. **The hand-out runs in one transaction, and only while the caller still waits.** `next` subscribes to the notifier (KTD6), then takes the oldest pending workflow and assigns it in one `InTx`. Before it assigns, it checks the request's context and the engine's stop. With no work it waits for a change, up to a 25-second window, and then returns nothing. The runner's call has no `http.Client` timeout, only a context deadline of the window plus a margin, so its client never gives up first.
- KTD6. **An in-process notifier wakes `next` and the followers, with a 1-second fallback.** Every write the engine makes (submit, assign, accept, update, log, done) fires one broadcast. A waiter subscribes before it reads, so a change between its read and its wait still wakes it. A tick every second re-checks anyway, which also covers a write the notifier never saw. Rejected: LISTEN/NOTIFY, which needs a dedicated connection and pays only once several engines share a database (slice 11).
- KTD7. **A step's log is `<log dir>/<database id>/<attempt id>/<position>.log`, created when the step starts and appended to by offset.**
  - Migration `00002` stores a random id in a one-row table, so a reset database never reuses an old build's files.
  - Once `StartStep` has committed, the engine creates the file if it is absent, never truncating it, so a file exists only for a step that really started.
  - `log` only appends to an existing file, under one lock per file, and writes before it answers. Bytes below the file's size are acknowledged and dropped; bytes past it are appended; an offset beyond the size is refused as `ErrInvalid`. The answer is always the size held.
  - The runner checks that every answer equals its offset plus its data's length, and treats anything else as a failed call.

  Rejected: naming files by ids alone, which shows an old build's output after a database reset with no error. Rejected: creating the file exclusively inside the step's transaction, which leaves a file for a step that never started when the commit fails, and blocks that step's start for good.
- KTD8. **The runner's log writer never blocks, and a finished step's log is complete.** The writer `Started` returns appends to an in-memory buffer. A sender per step ships chunks of at most 64 KiB every 250 ms, or sooner when a chunk is full. `Finished` waits for that step's buffer to drain, then sends the `finished` update. So the `finished` state is the architecture's "no more" marker, and `log` carries no final flag. A runner-side reason (a step that could not start, a shell killed by a signal, a failed write) goes into the step's log as one line starting `crew-actions:` and to the runner's stderr. A workspace that cannot be set up is reported on stderr, and the attempt is done with failure.

## Implementation Units

### U6. Engine: hand-out and reports

**Goal:** the engine hands a pending workflow to the runner and records its attempt, steps, logs and outcome.

**Requirements:** R2, R21; KTD2 to KTD8.

**Dependencies:** U1 to U5.

**Files:**
- Create `internal/engine/engine.go`, `internal/engine/notify.go`, `internal/engine/handout.go` and `internal/engine/report.go`.
- Create `internal/engine/notify_test.go`, `internal/engine/handout_test.go` and `internal/engine/report_test.go`.
- Delete `internal/engine/.gitkeep`.

**Approach:**
- The engine takes a store interface and a log interface declared in `engine.go`, plus a stop context.
- `Next` follows KTD5, using the notifier of KTD6.
- `Accept` reads the workflow's definition (U3), decodes it (KTD3) and calls `StartAttempt` with the step names.
- In `Update`, `running` runs `StartStep`, then creates the log file (KTD7), `finished` runs `FinishStep`, and `skipped` runs `SkipStep`.
- `Log` appends through the log interface.
- `Done` looks up the attempt's workflow and build (U3), then runs `FinishAttempt`, `FinishWorkflow` and `FinishBuild` with the workflow's outcome in one `InTx`.
- Every write fires the notifier.

**Patterns to follow:** the composed `InTx` happy path in `internal/store/postgres/attempts_test.go`.

**Test scenarios:** against `postgrestest` and a temporary log directory:
- Submit-equivalent setup with `CreateBuild`, then `Next` returns the workflow with version 2 and its three resolved steps.
- `Accept` with that version returns attempt 1, and the workflow is `running`. With version 1 it returns `ErrConflict`.
- `Next` with no work returns nothing after the window, which is shortened for tests. When a build is created while it waits, it returns that build's workflow at once.
- `Next` whose context is cancelled while it waits returns without assigning, and the workflow stays `pending`.
- Covers AE7. Updates for three steps where the second fails, then `Done` with failure: the steps, attempt, workflow and build hold their states and outcomes.
- `Update` with position 0, or one past the last step, returns `ErrInvalid`.
- After `Update` to `running`, the step's log file exists and is empty, even for a step that never writes.
- `Log` chunks follow U4's rule through the engine, and `Log` for a step never started returns `ErrInvalid`.
- A notifier waiter subscribed before a broadcast wakes, even when the broadcast comes before it starts waiting.

**Verification:** the scenarios pass with the test database, and `internal/engine` imports no transport, backend or source.
