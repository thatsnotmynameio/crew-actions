## Planning Contract

### Key Technical Decisions

- KTD3. **The stored definition is the compiled workflow, encoded as the protocol's `Workflow` message.** The engine runs `spec.Parse` once, at submit, which is where R8's refusal happens. It stores the name and resolved steps that `next` hands out and `accept` takes the step names from, as `model.Workflow.Definition`'s comment and the first migration already describe. Rejected: storing the file and parsing it again at hand-out, where a file a newer parser refuses would roll back the hand-out and stall the queue behind the oldest pending workflow.
- KTD6. **An in-process notifier wakes `next` and the followers, with a 1-second fallback.** Every write the engine makes (submit, assign, accept, update, log, done) fires one broadcast. A waiter subscribes before it reads, so a change between its read and its wait still wakes it. A tick every second re-checks anyway, which also covers a write the notifier never saw. Rejected: LISTEN/NOTIFY, which needs a dedicated connection and pays only once several engines share a database (slice 11).
- KTD9. **`Follow` diffs snapshots and log sizes, in an order that never shows a state before its output.** Each pass reads `GetBuild` first, as one consistent snapshot (`REPEATABLE READ`, read only), and the log sizes second. A step with no log file yet counts as 0 bytes. Because the runner drains a step's log before its `finished` update and the engine writes before it answers, every byte a snapshot's states imply is on disk by then. Per workflow, a pass sends:
  1. a workflow state change that is not `finished`;
  2. per attempt and step, a `running` it missed between passes, then any new output, then the terminal state;
  3. the workflow's `finished`;
  4. after every workflow, the build's end.

  Every stream starts from the beginning, and every event carries the attempt number, the position and, for output, its byte offset. The client drops what it already printed, keyed by attempt and position, so part 5's second attempt is never taken for a repeat. Rejected: a resume cursor on the server, which the client would have to dedupe against anyway.

## Implementation Units

### U7. Engine: submit and follow

**Goal:** a client submits a file and follows its build to the end, with states and output in an order that never shows a state before its output.

**Requirements:** R3, R4, R8, R9; KTD3, KTD9.

**Dependencies:** U6.

**Files:**
- Create `internal/engine/builds.go`, `internal/engine/follow.go`, `internal/engine/builds_test.go` and `internal/engine/follow_test.go`.

**Approach:**
- `Submit` refuses an empty identity part. It derives the workflow's name from the file name with `spec.NameFromPath`, runs `spec.Parse`, and turns any refusal into `ErrInvalid` with the parser's message. Only then does it call `CreateBuild`, with the encoded `Workflow` as the definition.
- `Follow` subscribes, then loops over passes as KTD9 orders them. Each pass sends output in chunks of at most 64 KiB, and the loop waits on the notifier, its tick and the engine's stop. It returns `ErrNotFound` for an unknown build and `ErrUnavailable` when the engine stops.

**Test scenarios:**
- Covers AE6. A file with `depends_on` returns `ErrInvalid` naming it, and no build exists. A misspelled `comands` names it as unknown.
- A valid file creates a build with the given identity and the file's base name.
- Following a finished build replays every state and its output, then the build's end, then returns.
- A pass whose snapshot already has the build finished still sends every step's terminal state and output before the workflow's `finished` and the build's end.
- A step that went `pending → running → finished` between two passes is sent as `running`, its output, then `finished`.
- Output appended while the stream is open arrives before that step's `finished`, and all output arrives before the build's end.
- A step whose output is larger than 64 KiB arrives as several chunks with increasing offsets.
- A step `running` in the snapshot with no log file yet sends no output, and the stream goes on.
- Following an unknown build returns `ErrNotFound`. Stopping the engine ends an open stream with `ErrUnavailable`.

**Verification:** the scenarios pass with the test database.
